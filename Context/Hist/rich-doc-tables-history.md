# История работ по таблицам в Rich Document

Документ фиксирует краткую историю работ по таблицам в rich-document редакторе. Это не политика текущей реализации, а хронология того, что делали по пользовательским промптам и где функциональность начала ломаться.

## 1. Базовая постановка

Первый запрос по таблицам был: сделать базовую поддержку таблиц в rich-document.

Требовалось:

- вставлять таблицу `m*n`;
- писать текст в ячейках;
- добавлять строки;
- удалять строки;
- добавлять столбцы;
- удалять столбцы;
- позже позволить размещать внутри ячеек inline-объекты, например картинки и видео.

На этом этапе таблица рассматривалась как часть содержимого rich-document, а не как отдельная бизнес-сущность.

## 2. Первая рабочая версия

Была сделана базовая вставка таблицы через toolbar.

Появились команды:

- вставить таблицу;
- добавить строку;
- удалить строку;
- добавить столбец;
- удалить столбец;
- удалить таблицу.

Таблица редактировалась прямо в rich-document редакторе, текст вводился в ячейки. Inline media логически оставались частью rich-text содержимого.

## 3. Заголовочная строка

Следующий запрос был про устойчивый toggle для заголовка таблицы.

Логика:

- если курсор стоит внутри таблицы и включен toggle `TH`, первая строка таблицы становится заголовочной;
- фон ячеек первой строки делается светло-серо-фиолетовым;
- текст первой строки становится жирным;
- toggle должен иметь устойчивое состояние, а не быть одноразовой кнопкой.

На этом этапе появилась кнопка `TH` на toolbar.

## 4. Нумерация строк

Дальше обсуждалась нумерация строк таблицы.

Изначально было предложено не сразу менять код, а оценить сложность. Базовая логика была такой:

- отдельный toggle `№`;
- при включении добавляется служебный первый столбец;
- если `TH` включен, первая строка служебного столбца содержит `№`, а нумерация начинается со второй строки;
- если `TH` выключен, нумерация начинается с первой строки;
- вставка выполняется только текстом в ячейку.

После обсуждения была сделана базовая версия нумерации.

## 5. Проблема сохранения и просмотра

После базовых операций обнаружилась проблема: в редакторе таблица выглядела нормально, но в режиме просмотра превращалась в линейный текст.

Симптом:

- в edit mode таблица была настоящей таблицей;
- в readonly mode ячейки шли строками текста;
- при возвращении в edit mode таблица снова выглядела как таблица.

Причина была в том, что readonly renderer и cache не восстанавливали таблицу как HTML table.

Была зафиксирована политика:

- таблица должна быть отдельным `RichTextBlock`;
- `table/tr/td/th` должны переживать цикл `save -> reload -> edit`;
- readonly режим должен отображать таблицу так же, как edit режим;
- `HtmlCache` не является canonical storage, но должен строиться из table block.

Поскольку данные были тестовыми, сохранность текущего тестового содержимого не была критичной.

## 6. Выравнивание readonly и edit

После правок было сделано так, чтобы в режиме просмотра таблица выглядела так же, как в режиме редактирования:

- таблица не разворачивалась в plain text;
- границы ячеек были видимы;
- заголовочная строка сохраняла оформление;
- нумерация строк отображалась как в редакторе;
- таблица растягивалась на доступную ширину.

Также была создана политика таблиц:

```text
Context/Policy/RichDocument/Tables/rich-doc-tables-policy.md
```

## 7. Обсуждение ручной ширины столбцов

Следующим пунктом была ручная настройка ширины столбцов.

Обсуждались варианты:

- хранить ширину не как произвольный `style`, а как whitelist-атрибут;
- использовать атрибут вроде `data-rich-col-width="240"`;
- потом строить `colgroup` или inline-safe width при render;
- не ломать текущий table roundtrip.

После обсуждения был начат шаг 1 по ручной ширине столбцов.

## 8. Мышиный drag-resize столбцов

После того как базовая ручная настройка ширин заработала, был следующий запрос: сделать изменение ширины столбцов мышкой.

Цель:

- при наведении на границу столбца показывать возможность resize;
- при drag менять ширину столбца;
- сохранять результат в структуре таблицы;
- не ломать текущий edit/readonly roundtrip.

Именно на этом этапе функциональность начала вести себя нестабильно.

## 9. Первая проблема после drag-resize

После добавления мышиного resize обнаружилось, что при наведении курсора к ячейке менялась высота ячеек.

Симптом:

- в обычном состоянии таблица выглядела нормально;
- при наведении на границу или ячейку высота строк прыгала;
- визуально таблица сдвигалась, хотя пользователь еще не выполнял resize.

Пробовали исправить это так, чтобы resize handles не влияли на layout таблицы.

## 10. Вторая проблема: правая граница таблицы

Следующая проблема была с правой границей.

Симптом:

- при приближении resize к правой границе она тоже начинала двигаться;
- таблица съезжала;
- появлялся горизонтальный скролл;
- правая внешняя граница вела себя как перетаскиваемая, хотя должна быть фиксированной.

Требование было:

- левая и правая внешние границы таблицы не перетаскиваются;
- они не двигаются при приближении resize других колонок;
- resize работает только для внутренних границ столбцов.

## 11. Точка поломки

После попытки зафиксировать внешние границы и поправить drag-resize стало хуже.

Симптомы:

- во время drag перестал быть виден сам процесс перетаскивания;
- раньше визуальный процесс drag был виден, после правки он пропал;
- в одной сессии редактирования работало только одно перетаскивание;
- последующие попытки resize уже не выполнялись;
- пользовательское ощущение: "что-то пошло не так".

Это и есть точка, где функциональность таблиц перестала нормально работать: после реализации drag-resize столбцов мышкой и последующих попыток ограничить правую/левую внешние границы таблицы.

## 12. Текущий вывод

Базовая функциональность таблиц была рабочей до темы drag-resize:

- вставка таблицы;
- ввод текста;
- строки и столбцы;
- заголовок `TH`;
- нумерация `№`;
- сохранение таблицы;
- просмотр таблицы как таблицы.

Нестабильность началась именно на механике mouse drag-resize столбцов.

Перед повторной реализацией resize стоит идти осторожнее:

- сначала зафиксировать storage ширин без mouse drag;
- потом добавить чистый визуальный hover, который не меняет layout;
- затем добавить drag только для внутренних границ;
- обязательно проверить несколько resize подряд в одной edit-сессии;
- отдельно проверить правую внешнюю границу и отсутствие горизонтального скролла.

## 13. Повторная реализация после отката

После отката табличных изменений drag-resize был реализован повторно более консервативно:

- используется штатный механизм resize из Tiptap/ProseMirror tables;
- `lastColumnResizable=false`, чтобы правая внешняя граница не была resize-handle;
- resize-handle рисуется как absolute overlay внутри ячейки и не должен менять высоту строк;
- canonical storage ширин сделан через whitelist-атрибут `data-colwidth`;
- `data-colwidth` пропускается через sanitizer при сохранении;
- readonly `HtmlCache` строит безопасный derived width/style из `data-colwidth`, но не считает style canonical storage.

Цель этой реализации - не повторять ошибку старой кастомной механики, где после фикса внешних границ перестал отображаться процесс drag и работал только один resize в edit-сессии.
