# Политика хранения данных: графовая система хранения

## 1. Общий принцип

В системе используется **графовая модель хранения данных**.

Ее базовая идея:

- экземпляры объектов хранятся отдельно
- экземпляры связей между объектами хранятся отдельно
- полезные данные объектов хранятся отдельно

Базовая модель строится на трех слоях хранения:

1. `BusinessEntity`
2. `Relation`
3. `BusinessEntityData`

Это не описание конкретных доменных типов, а универсальная архитектурная схема хранения.

---

## 2. Концепция

Система исходит из того, что есть три разные сущности хранения:

- **объект**
- **связь**
- **данные объекта**

Они не смешиваются в одной записи.

Это значит:

- объект не обязан содержать свое содержимое внутри себя
- объект не обязан хранить свои связи как встроенные поля
- структура предметной модели задается не вложенностью записей, а отдельным графом отношений

Такой подход позволяет строить систему, где модель данных богаче и гибче, чем обычное дерево или набор жестких таблиц под каждый тип.

---

## 3. Слой `BusinessEntity`

`BusinessEntity` хранит **сам факт существования объекта**.

Это универсальная запись, представляющая отдельный экземпляр сущности предметной области.

Типовая ответственность `BusinessEntity`:

- идентичность объекта
- базовые метаданные объекта
- тип объекта
- общие системные поля

Типовые поля:

- `Id`
- `Name`
- `CreatedDate`
- `LastModifiedDate`
- `EntityType`
- другие базовые атрибуты, одинаково относящиеся ко всем объектам

### Что должно храниться в `BusinessEntity`

В `BusinessEntity` должно храниться только то, что описывает сам объект как единицу графа:

- кто это
- как он называется
- какого он типа
- когда он создан и изменен

### Что не должно храниться в `BusinessEntity`

В `BusinessEntity` не должны напрямую жить:

- большие полезные данные
- содержимое объекта
- граф связей
- временное UI-состояние
- инфраструктурное состояние исполнения

`BusinessEntity` отвечает за существование объекта, но не за его содержимое и не за его связи.

---

## 4. Слой `Relation`

`Relation` хранит **связь между двумя объектами**.

Каждая запись `Relation` представляет одно ребро графа.

Типовая ответственность `Relation`:

- задать факт связи между двумя объектами
- задать направление связи
- задать тип связи
- при необходимости хранить параметры связи

Типовые поля:

- `Id`
- `ObjectAId`
- `ObjectBId`
- `RelationType`
- `RelationParams`
- `CreatedDate`
- `LastModifiedDate`

### Главное правило

Структурные и смысловые отношения между объектами должны моделироваться через `Relation`, а не через жесткое встраивание parent/child-полей в сам объект на каждый новый сценарий.

То есть по умолчанию:

- объект не знает все свои связи изнутри
- связь задается отдельной записью

Это дает системе:

- возможность иметь несколько разных типов отношений
- возможность иметь несколько разных представлений структуры
- слабую связанность между моделью объекта и моделью графа

---

## 5. Слой `BusinessEntityData`

`BusinessEntityData` хранит **полезную нагрузку объекта** отдельно от самого объекта.

Типовая ответственность `BusinessEntityData`:

- содержимое объекта
- большие данные объекта
- изменяемые данные, не являющиеся его идентичностью
- сериализованная или структурированная payload-часть

Типовые поля:

- `Id`
- `EntityId`
- `Data`
- `CreatedDate`
- `LastModifiedDate`

### Главное правило

Если данные логически являются содержимым объекта, а не самим объектом, они должны храниться отдельно от `BusinessEntity`.

Это особенно важно, если:

- данные могут быть большими
- данные могут часто меняться
- формат данных может развиваться отдельно
- один объект может иметь один или несколько блоков payload-данных

---

## 6. Формула хранения

Графовая формула хранения выглядит так:

```text
BusinessEntity
  = объект

Relation
  = связь между объектами

BusinessEntityData
  = данные объекта
```

В графическом виде:

```text
[BusinessEntity A] ---- Relation ---- [BusinessEntity B]
        |
        +---- BusinessEntityData
```

Это базовая модель, от которой строится дальнейшая предметная структура.

---

## 7. Используемые репозитории

На уровне доступа к данным система использует единый обобщенный контракт репозитория:

- `IAsyncRepository<T>`

Этот интерфейс является базовой точкой работы с графовым storage для всех DTO, через которые хранение читается и сохраняется.

Базовый набор репозиториев в системе:

- `IAsyncRepository<BusinessEntityDto>`
- `IAsyncRepository<BusinessEntityRelationDto>`
- `IAsyncRepository<BusinessEntityPropertyDto>`
- `IAsyncRepository<BusinessEntityDataDto>`

### Как репозитории соотносятся с концепцией хранения

Концептуально графовая модель по-прежнему делится на три слоя:

- объект
- связь
- данные / свойства объекта

На уровне repository-слоя этим слоям соответствуют DTO-типы:

- `BusinessEntityDto`
  техническое представление узла графа, его идентичности и базовых атрибутов
- `BusinessEntityRelationDto`
  техническое представление ребра графа
- `BusinessEntityPropertyDto`
  техническое представление отдельных свойств объекта
- `BusinessEntityDataDto`
  техническое представление сериализованного бизнес-объекта или его крупного payload-блока

### Ответственность каждого репозитория

`IAsyncRepository<BusinessEntityDto>` отвечает за:

- создание объектов графа
- чтение объектов по id
- выборки по типам объектов
- обновление базовых атрибутов объекта
- удаление объектов

`IAsyncRepository<BusinessEntityRelationDto>` отвечает за:

- создание связей между объектами
- чтение входящих и исходящих связей
- фильтрацию по типу связи
- изменение и удаление связей

`IAsyncRepository<BusinessEntityPropertyDto>` отвечает за:

- чтение отдельных свойств объекта
- сохранение типоспецифичных полей объекта в атомарном виде
- обновление набора свойств
- удаление свойств, связанных с объектом

`IAsyncRepository<BusinessEntityDataDto>` отвечает за:

- чтение сериализованного бизнес-объекта
- сохранение целостного snapshot или payload объекта
- хранение крупных структурированных данных объекта
- версионирование сериализованного представления при необходимости

### Главный принцип repository-слоя

Репозитории не меняют архитектуру хранения и не смешивают ответственности.

Они лишь предоставляют единый асинхронный способ работать с базовыми DTO-представлениями storage-слоя:

- `BusinessEntityDto` для узлов
- `BusinessEntityRelationDto` для связей
- `BusinessEntityPropertyDto` для атомарных свойств
- `BusinessEntityDataDto` для сериализованных бизнес-объектов

### Предполагаемый состав DTO

Ниже приведен предварительный состав полей, скорректированный по аналогии с текущими сущностями в коде:

- `BusinessEntity.Core.Classes.BusinessEntity`
- `BusinessEntity.Core.Classes.BusinessEntityBase`
- `BusinessEntity.Core.Classes.Relation`
- `BusinessEntity.Core.Classes.BusinessEntityData`
- `BusinessEntity.Core.Classes.BaseEntity`

Это не окончательная схема, а стартовая гипотеза для дальнейшего уточнения.

### Что реально подтверждено текущим кодом

В текущем коде уже явно подтверждены следующие общие поля:

- `ObjectAId`
- `ObjectBId`
- `RelationType`
- `RelationParams`

Для payload-данных уже подтверждены:

- `EntityId`
- `Data`

### Предлагаемый состав `BusinessEntityRelationDto`

### Краткая логика распределения полей

`BusinessEntityDto` должен содержать:

- идентичность объекта
- тип объекта
- базовые атрибуты объекта

`BusinessEntityRelationDto` должен содержать:

- факт связи между двумя объектами
- тип и параметры связи
- служебные поля порядка и состояния связи

`BusinessEntityPropertyDto` должен содержать:

- отдельные адресуемые свойства объекта
- значения, удобные для точечной фильтрации
- компактные метаданные

`BusinessEntityDataDto` должен содержать:

- сериализованный объект целиком или крупный payload
- данные, которые удобнее читать и сохранять единым блоком
- служебную информацию о формате сериализации

### Предполагаемое разделение между Property и Data

`BusinessEntityPropertyDto` предназначен для:

- отдельных типоспецифичных полей
- метаданных
- значений, по которым может понадобиться адресная фильтрация
- компактных свойств объекта

`BusinessEntityDataDto` предназначен для:

- сериализованного бизнес-объекта целиком
- больших payload-блоков
- сложных структур, которые удобно хранить как единое сериализованное представление
- snapshot-представления объекта для восстановления или интеграции

## 8. Почему выбрана именно такая модель

Такая модель выбрана, потому что она:

- графовая
- универсальная
- расширяемая
- не привязана к одному конкретному набору типов объектов
- не привязана к одному конкретному виду иерархии
- позволяет эволюционировать предметную модель без взрыва числа таблиц

Она удобна для систем, где:

- состав типов объектов может расти
- виды связей могут расти
- объектная модель и модель связей развиваются независимо
- UI может показывать дерево, граф, список или другие представления одной и той же модели

---

## 9. Политика добавления новых типов объектов

При появлении нового типа объекта по умолчанию **не нужно создавать отдельную таблицу**.

Новый тип сначала должен рассматриваться как новый вариант `BusinessEntityType`.

Базовый порядок:

1. определить новый тип объекта
2. представить его как `BusinessEntity`
3. описать его связи через `Relation`
4. хранить его полезные данные в `BusinessEntityData`, если они нужны

### Когда отдельная таблица допустима

Отдельная таблица допустима только если новый тип:

- имеет собственную тяжелую и специализированную структуру
- требует отдельной модели хранения
- требует отдельной производительной оптимизации
- логически уже выходит за рамки универсальной сущности графа

Но это должно быть исключением, а не правилом.

По умолчанию система предпочитает:

- общую сущность объекта
- общую сущность связи
- общую сущность данных

---

## 10. Политика добавления новых связей

Новый вид отношения между объектами должен добавляться как новый `RelationType`, а не как встраивание специального поля в `BusinessEntity`.

Правила:

- связь должна быть типизированной
- смысл связи должен быть доменно понятным
- направление связи должно быть однозначным
- дополнительные параметры связи допускается хранить в `RelationParams`

Таким образом расширяется именно граф, а не разрастается схема объекта.

---

## 11. Что считается правильным использованием модели

Правильно:

- хранить объект как `BusinessEntity`
- хранить отношение между объектами как `Relation`
- хранить payload объекта как `BusinessEntityData`
- строить структуру через набор связей
- отделять идентичность объекта от его данных

Неправильно:

- смешивать объект, его связи и его содержимое в одной сущности
- кодировать все отношения только через специальные поля в объекте
- создавать отдельную таблицу под каждый новый тип без сильной причины
- хранить временное UI-состояние в графовом хранилище

---

## 12. Ограничения и договоренности

Система хранения должна соблюдать следующие договоренности:

- `BusinessEntity` отвечает за идентичность и базовые атрибуты
- `Relation` отвечает за граф связей
- `BusinessEntityData` отвечает за полезную нагрузку
- `IAsyncRepository<T>` является стандартным способом доступа к каждой базовой сущности хранения
- `IAsyncRepository<BusinessEntityDto>` используется для узлов графа
- `IAsyncRepository<BusinessEntityRelationDto>` используется для связей графа
- `IAsyncRepository<BusinessEntityPropertyDto>` используется для атомарных свойств объекта
- `IAsyncRepository<BusinessEntityDataDto>` используется для сериализованного представления бизнес-объекта
- структура графа не должна смешиваться с временным состоянием исполнения
- новые типы по умолчанию добавляются через типизацию `BusinessEntity`
- новые отношения по умолчанию добавляются через `Relation`

---

## 13. Перспектива расширения

Базовое ядро графовой системы хранения состоит из трех сущностей:

- `BusinessEntity`
- `Relation`
- `BusinessEntityData`

В будущем система может расширяться дополнительными таблицами и слоями, если появится новая самостоятельная ответственность.

Но базовая архитектурная политика остается неизменной:

- объекты отдельно
- связи отдельно
- данные отдельно

Это и есть фундамент графовой системы хранения в проекте.
