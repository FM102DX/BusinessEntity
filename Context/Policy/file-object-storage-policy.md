# Политика хранения файловых объектов

## 1. Назначение

Этот документ фиксирует правила хранения файловых объектов, которые создаются или загружаются пользователем в системе `BusinessEntity`.

К файловым объектам относятся:

- изображения, вставленные в rich document;
- вложения документов;
- архивы;
- импортированные или сгенерированные файлы;
- любые будущие binary/file объекты, которые относятся к конкретному `BusinessEntity`.

Главная цель политики: файловые объекты не должны теряться при пересоздании Docker-контейнеров приложения.

---

## 2. Главный принцип

Файлы нельзя хранить во внутренней файловой системе контейнера как в постоянном хранилище.

Контейнер приложения считается disposable runtime:

```text
container filesystem = временный слой исполнения
external storage      = постоянное хранилище файлов
database              = постоянное хранилище метаданных и ссылок
```

Если файл должен переживать:

- `docker compose up --build`;
- пересоздание контейнера;
- рестарт приложения;
- обновление образа;

он обязан быть сохранен во внешнем storage root.

---

## 3. Рекомендуемая модель для текущей среды

Для текущей локальной и тестовой среды используется внешний каталог хоста, примонтированный в контейнер приложения через Docker bind mount.

Пример host-каталога:

```text
C:\Develop\BusinessEntityStorage
```

Пример mount внутри контейнера:

```text
/app/storage
```

Приложение должно работать только с container-path, полученным из конфигурации:

```json
"Storage": {
  "RootPath": "/app/storage"
}
```

Код приложения не должен зависеть от Windows-пути хоста.

---

## 4. Структура storage root

Все объекты, относящиеся к конкретному `BusinessEntity`, хранятся внутри каталога этого `BusinessEntity`.

Базовая структура:

```text
{StorageRoot}/
  business-entities/
    {businessEntityId}/
      images/
      attachments/
      archives/
      generated/
      temp/
```

Назначение каталогов:

- `images` - изображения, вставленные в rich document или связанные с документом;
- `attachments` - пользовательские вложения;
- `archives` - архивы и пакетные выгрузки;
- `generated` - файлы, созданные системой;
- `temp` - временные файлы, которые могут быть очищены регламентной процедурой.

Допускается добавлять новые подкаталоги, если появляется новый тип файлового объекта.

---

## 5. Идентичность файлового объекта

Каждый сохраняемый файловый объект должен иметь стабильный logical id.

Рекомендуемая схема:

```text
FileObjectId = Guid
```

Физическое имя файла на диске не должно напрямую зависеть от пользовательского имени файла.

Рекомендуемый формат:

```text
{fileObjectId}.{extension}
```

Оригинальное имя файла хранится в метаданных, а не используется как главный ключ хранения.

Причины:

- пользовательские имена могут конфликтовать;
- в именах могут быть недопустимые символы;
- оригинальное имя может раскрывать лишнюю информацию;
- файл может быть переименован пользователем без физического перемещения.

---

## 6. Метаданные

БД хранит метаданные файлового объекта, а не сам файл.

Минимальный набор метаданных:

- `FileObjectId`;
- `BusinessEntityId`;
- logical type: `Image`, `Attachment`, `Archive`, `Generated`, etc.;
- relative path внутри `StorageRoot`;
- original file name;
- content type;
- file size;
- created date/time;
- created by user id;
- optional checksum;
- optional width/height для изображений.

В БД нельзя хранить absolute host path.

Правильная ссылка:

```text
business-entities/{businessEntityId}/images/{fileObjectId}.png
```

Неправильная ссылка:

```text
C:\Develop\BusinessEntityStorage\business-entities\...
```

---

## 7. Rich document images

Изображение, вставленное в rich document, считается частью документа как бизнес-смысла, но физически хранится как файловый объект.

В тексте rich document хранится не binary image, а маркер/HTML-представление со ссылкой на logical image id.

Пример canonical marker внутри rich-text inline HTML:

```html
<span class="rich-text-inline-image"
      data-rich-image-id="9f7c4b2d-2e1f-4d4c-ae8e-0d7c9a1a7d33"
      data-display-variant="original"
      data-width="300"></span>
```

В rendered HTML это может превращаться в:

```html
<span class="rich-text-inline-image"
      data-rich-image-id="9f7c4b2d-2e1f-4d4c-ae8e-0d7c9a1a7d33"
      data-display-variant="original"
      data-width="300">
  <img data-rich-image-id="9f7c4b2d-2e1f-4d4c-ae8e-0d7c9a1a7d33"
       src="/rich-document-files/.../images/9f7c4b2d-2e1f-4d4c-ae8e-0d7c9a1a7d33/original"
       width="300" />
</span>
```

Размер изображения, выбранный пользователем в редакторе, хранится в rich document content, а не только в UI state.

Физический файл изображения хранится в:

```text
business-entities/{businessEntityId}/images/{imageId}/
  metadata.json
  original.{nativeExtension}
```

Файл variant хранится в родном формате, с которым он был загружен или сгенерирован. Для вставленной PNG-картинки это `original.png`, для JPEG - `original.jpg`, для WebP - `original.webp`.

`metadata.json` хранит как минимум:

```json
{
  "fileName": "image.png",
  "contentType": "image/png",
  "storedFileName": "original.png"
}
```

Использование технического `original.bin` для новых файлов запрещено. Старые `.bin`-файлы допустимы только как legacy input при чтении или миграции.

---

## 8. Версионирование и файлы

Версионирование rich document версионирует содержимое документа, включая ссылки на файловые объекты и параметры их отображения.

Сам физический файл не обязан копироваться при каждой новой версии документа.

Правило:

```text
Если новая версия документа ссылается на тот же image id, используется тот же файл.
Если пользователь вставил новую картинку, создается новый FileObjectId.
Если пользователь заменил файл картинки, это новый FileObjectId.
```

Удаление ссылки на изображение из новой версии документа не означает немедленное физическое удаление файла, потому что старые версии документа могут продолжать на него ссылаться.

Физическая очистка orphan files должна выполняться отдельной процедурой, которая проверяет ссылки во всех версиях документа.

---

## 9. Доступ к файлам

Файлы не должны отдаваться как произвольные static files без проверки контекста.

Рекомендуемый доступ:

```text
GET /rich-document-files/{businessEntityId}/images/{fileObjectId}
GET /business-entity-files/{businessEntityId}/{fileObjectId}
```

Endpoint должен:

- проверить, что файл относится к указанному `BusinessEntity`;
- проверить права текущего пользователя;
- определить content type;
- вернуть файл из external storage;
- не раскрывать absolute path на диске.

Для временных или публичных ссылок можно добавить отдельный механизм позже.

---

## 10. Безопасность

При сохранении файла обязательно:

- не доверять оригинальному имени файла;
- нормализовать и контролировать расширение;
- проверять допустимые content types;
- ограничивать максимальный размер файла;
- запрещать path traversal (`../`, absolute paths, спецсимволы пути);
- сохранять файл только внутри `StorageRoot`;
- при необходимости считать checksum.

Для изображений дополнительно желательно:

- проверять, что файл действительно является изображением;
- читать фактические dimensions;
- не исполнять SVG как активный контент, если SVG будет разрешен.

---

## 11. Временные файлы

Каталог:

```text
business-entities/{businessEntityId}/temp/
```

предназначен только для промежуточных файлов.

Файлы из `temp`:

- не считаются постоянными;
- могут быть удалены регламентной очисткой;
- не должны использоваться как canonical ссылка из документа или бизнес-данных.

Если временный файл становится частью документа или вложением, он должен быть перемещен в постоянный каталог (`images`, `attachments`, `archives`, etc.) и получить `FileObjectId`.

---

## 12. Production-вариант

Текущая политика допускает замену локального external storage на объектное хранилище без изменения бизнес-логики.

Целевая production-альтернатива:

- S3-compatible storage;
- MinIO;
- cloud object storage.

Для этого код должен работать через storage abstraction:

```text
IFileObjectStorage
```

а не напрямую через `File.*` во всех местах бизнес-логики.

Минимальные операции abstraction:

- save;
- read/open stream;
- delete;
- exists;
- get metadata;
- build serving URL or file token.

---

## 13. Запрещено

Запрещено:

- сохранять постоянные файлы только внутри контейнера;
- хранить absolute host paths в БД;
- использовать пользовательское имя файла как физический ключ;
- удалять физический файл, не проверив ссылки из старых версий документов;
- читать или отдавать файл по произвольному path из запроса;
- смешивать временные и постоянные файлы в одном каталоге без метаданных.
